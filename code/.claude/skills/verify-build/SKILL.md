# Проверка сборки

Выполнять по порядку. **Любой красный шаг = задача не выполнена.** Не сообщать
о готовности, не переходить к следующей задаче и не мержить, пока не зелено.

## 1. Статические проверки

```bash
yarn install --frozen-lockfile
yarn typecheck
yarn lint
```

Только yarn. `npm` и `npx` в этом проекте не используются — если в выводе
или в изменениях появился `package-lock.json`, удалить его и разобраться, откуда взялся.

`typecheck` должен идти без `--noEmit`-обходов и без новых `@ts-expect-error`.
Если добавили подавление ошибки — объяснить в отчёте, почему иначе нельзя.

## 2. Границы FSD

```bash
yarn lint            # правило boundaries/steps-to-use-imports
git diff --name-only # посмотреть, какие слои затронуты
```

Проверить руками по изменённым файлам:

- импорт идёт только вниз по слоям `app → pages → widgets → features → entities → shared`;
- нет импортов вбок внутри одного слоя;
- нет импортов во внутренности слайса в обход `index.ts`
  (`entities/pet/model/store` вместо `entities/pet` — нарушение);
- новый код лежит в правильном слое: формула — в `entities`, сценарий действия —
  в `features`, композитный блок — в `widgets`, экран — в `pages`.

Нарушение границ — блокирующая ошибка, даже если код работает.

## 3. Tests first — проверка порядка

```bash
git log --oneline --stat -5
yarn test --ci
```

Правила:

- **Тест должен быть написан до реализации и наблюдаться красным.** В отчёте
  явно указать: какой тест писался первым, с какой ошибкой падал, что сделало
  его зелёным. «Тест есть» ≠ «тест был первым».
- Если работа велась не в этом порядке — не задним числом дописывать тест
  и объявлять TDD. Честно указать в отчёте, что порядок нарушен.
- Новая чистая функция в `entities/*/lib` (формула экономики, расчёт прогресса)
  **обязана** иметь unit-тест на поведение и на границы: 0 монет, трата больше
  баланса, максимальный уровень, длинный перерыв, повторный тап.
- Тест формулируется от поведения, а не от реализации.
- Падающий тест не «чинится» через `.skip` или ослабление ассерта. Либо код
  неверен, либо тест неверен — определить, что именно, и написать это в отчёте.

## 4. Android-сборка

```bash
cd android && ./gradlew assembleDebug && cd ..
```

Прогон должен закончиться `BUILD SUCCESSFUL`. Варнинги про deprecated API
допустимы, ошибки линковки нативных модулей — нет.

## 5. Запуск на эмуляторе

```bash
adb devices                    # убедиться, что эмулятор поднят
yarn android
```

Проверить:
- приложение стартует и доходит до первого экрана, без красного экрана смерти;
- в `adb logcat -s ReactNativeJS:V` нет ошибок и новых варнингов от нашего кода;
- изменённый экран действительно открывается и работает — не «собралось, значит ок».

## 6. Чек-лист RuStore (перед подготовкой релиза)

Прогонять только при работе над релизной сборкой, не на каждой фиче:

- `android/app/build.gradle`: `versionCode` инкрементирован, `versionName` осмысленный
- `minSdkVersion` ≥ 24, `targetSdkVersion` соответствует актуальному требованию RuStore
- в `AndroidManifest.xml` нет лишних разрешений (для этого приложения не нужны
  ни камера, ни геолокация, ни контакты, ни `INTERNET`, если нет бэкенда)
- нет сервисов Google Play (GMS/Firebase) как обязательной зависимости —
  устройства без GMS должны работать
- `./gradlew bundleRelease` собирается и AAB подписан релизным ключом
- возрастная маркировка и отсутствие рекламы/покупок соответствуют описанию в карточке

## Отчёт

Завершить кратким итогом: какие шаги прошли, что упало, что осталось непроверенным
и почему. Не писать «всё работает», если шаг 5 не выполнялся — писать, что он пропущен.
