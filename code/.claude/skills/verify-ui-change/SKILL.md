# Проверка UI-изменения

Цель — увидеть изменение своими глазами в работающем приложении, а не
предположить, что оно работает, потому что код скомпилировался.

## 1. Поднять приложение

```bash
yarn start --reset-cache   # в фоне
yarn android
```

Дойти навигацией до изменённого экрана как это сделает ребёнок — с холодного
старта, а не через deeplink-хак.

## 2. Снять доказательства

```bash
adb exec-out screencap -p > /tmp/after.png
```

Сделать скриншот до и после (если «до» уже недоступно — описать словами, что было).
Приложить скриншоты к отчёту. Для анимаций — записать `adb shell screenrecord`
или описать покадрово, что происходит.

## 3. Провзаимодействовать

Не просто посмотреть — нажать. Проверить:
- happy path работает;
- быстрые повторные нажатия не ломают состояние и не удваивают эффект;
- что происходит на пустом состоянии (0 монет, нет питомца, нет заданий);
- что происходит на граничном (очень длинное имя питомца, большое число монет);
- возврат назад и повторный вход на экран не теряет и не дублирует данные.

## 4. Сверить с UI-kit

Открыть `src/shared/ui/`. Проверить:

- **Не создан ли компонент, который уже есть в ките.** Собственная кнопка,
  свой прогресс-бар, свой тост вместо `GameButton` / `ProgressBar` / `Toast` —
  блокирующая находка. Экран собирается из кита, а не верстается заново.
- Если компонент в кит всё-таки добавлен: его props-контракт записан
  в `src/shared/ui/` **до** реализации, у него есть тест, и он показан
  на demo-экране `pages/ui-kit-demo`.
- Соблюдены инварианты кита: тач-таргет ≥ 44×44 dp, `disabled` всегда идёт
  с `disabledReason`, у нажатия есть визуальный + тактильный + звуковой отклик,
  анимации уважают reduce-motion.
- Открыть demo-экран кита и убедиться, что изменение компонента не сломало
  другие его состояния.

## 5. Сверить с брендбуком

Открыть `src/shared/theme/`. Проверить:
- цвета взяты из `src/shared/theme` и соответствуют палитре брендбука —
  **хардкодных hex в компоненте быть не должно**;
- шрифты, кегли и начертания из брендбука;
- отступы кратны сетке брендбука;
- иллюстрации и иконки в разрешённом стиле;
- тон текстов соответствует гайду.

### Режим заглушки

Официального брендбука у нас пока нет, тема работает на
`shared/theme/placeholder.ts`. Это **не повод останавливать работу** —
но и не повод подставлять значения на глаз.

Проверять надо не «совпадает ли цвет с брендбуком», а **готовность к подмене**:

- компонент берёт значения из темы, а не из литералов;
- нужного токена не хватило → он добавлен в `ThemeContract` и в обе темы,
  а не захардкожен в компоненте;
- ни одного hex-литерала, размера шрифта или отступа вне `shared/theme`;
- вёрстка не разъедется, если значения токенов поменяются: не завязывайся
  на конкретную высоту строки или ширину, вытекающие из текущих чисел.

Правило: **после получения брендбука экран должен стать правильным от замены
одного файла темы.** Если для этого понадобится трогать компонент — шаг не пройден.

Если правило вообще отсутствует как понятие (не «какое значение», а «какой
токен нужен») — зафиксировать в отчёте как открытый вопрос к дизайну.

## 6. Проверка «глазами ребёнка 7 лет»

- Понятно ли, что делать на экране, **без чтения текста** — по иконкам и картинке?
- Все интерактивные элементы ≥ 44×44 dp — палец ребёнка попадает?
- Есть ли текст, который ребёнок 7 лет не прочитает или не поймёт
  («баланс», «депозит», «приоритизация»)? Заменить на детскую формулировку.
- Может ли ребёнок случайно потерять прогресс без подтверждения?
- Нет ли механики, которая создаёт тревогу (таймер, угроза, наказание)?

## 7. Логи

```bash
adb logcat -s ReactNativeJS:V
```

Ноль ошибок и ноль новых варнингов от нашего кода. Особое внимание — варнинги про
ключи в списках, обновление state на размонтированном компоненте, утечки таймеров
анимаций.

## 8. Регресс

```bash
yarn typecheck && yarn test --ci
```

## Отчёт

Скриншоты + что проверил + что не смог проверить и почему + открытые вопросы
к дизайну. Если хоть один пункт не выполнен — писать «не готово», а не «готово с оговорками».
